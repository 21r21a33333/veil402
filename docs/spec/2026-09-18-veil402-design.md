# Veil402 — Design Spec (MVP)

Private agent payments on Solana: **private by default, provable on demand.** A shielded UTXO pool
giving amount + recipient privacy, with per-transaction, per-verifier selective disclosure for
single-payment auditability. Grounded in `docs/research/01-prior-art-and-primitives.md`.

Status: **design — pending review.** No implementation until this spec is approved.

---

## 1. Goals & non-goals

**Goals (MVP)**
- Shield SPL tokens, transfer them privately (amount + recipient hidden), and unshield to a
  transparent address.
- One seed → all keys; unlinkable addresses; a wallet that can recover from seed alone.
- Per-tx, per-verifier, nonce-bound **selective disclosure** of a single payment.
- Everything verifiable on-chain (Groth16 via CPI) or off-chain (disclosure) with real transactions.

**Non-goals (explicitly out of MVP)**
- Variable n/m transactions (fixed 2-in/2-out only).
- FMD/OMR note discovery (trial-decryption for MVP).
- Compliance proofs (RAILGUN-style Proof-of-Innocence) — separate axis, later.
- Cross-chain, a relayer *network*, a token, governance. (A single optional relayer/paymaster for
  gasless unshield is a stretch goal, not core.)
- Formal audit (this is an MVP; "not audited" until a real audit).

## 2. Locked decisions
| Axis | Decision |
|---|---|
| Tx schema | fixed **2-in / 2-out** join-split; dummy (value-0) notes cover deposit/withdraw/transfer/merge/split |
| Proving | **Noir → Sunspot → Groth16**, verified on-chain by CPI (Phase-1-proven) |
| Assets | **one multi-asset pool**, `asset_id` (SPL mint) is a private note field; per-tx single-asset |
| Keys/UX | **single BIP-39 seed → HD derivation**; Baby Jubjub keys; diversified addresses; watch-only via `ivk` |
| Auditability | **per-tx, per-verifier, nonce-bound ZK disclosure**; never share the viewing key |
| Discovery | on-chain encrypted notes + trial-decryption + light indexer |

## 3. Cryptographic primitives
- **SNARK field:** BN254 scalar field. **Proving:** Groth16 (Sunspot from Noir ACIR).
- **Hash:** Poseidon (circom/BN254 params) — in-circuit and via Solana `sol_poseidon` syscall
  (byte-identical, proven in Phase 1). Used for commitments, nullifiers, Merkle nodes, key derivation.
- **Embedded curve (keys, ECDH, signatures):** **Baby Jubjub** (BN254-embedded, circomlib-standard;
  same choice as RAILGUN). Key pairs, ECDH for note encryption, and EdDSA-Poseidon signatures all
  operate here so they are cheap in-circuit.
- **AEAD:** ChaCha20-Poly1305 for note ciphertext (off-circuit).
- **KDF:** Poseidon for in-circuit/field derivations; Blake2b for off-circuit byte derivations.

> Phase 2.0 crypto spike validates the exact Baby Jubjub + EdDSA-Poseidon + diversifier params in
> Noir before the transaction circuit is built.

## 4. Key hierarchy, addresses, and what the user stores

Derived from one seed (RAILGUN construction + Zcash-style diversification):
```
seed  (BIP-39 mnemonic)                         ← the ONLY thing the user backs up
 ├─ spendingKey        (Baby Jubjub scalar)      → spendingPubKey = spendingKey · G
 └─ viewingKey         (Baby Jubjub scalar)      → viewingPubKey  = viewingKey · G   (ECDH + scan)
     ├─ nullifyingKey nk = Poseidon(viewingKey)
     ├─ ivk (incoming) = viewingKey              → detect + decrypt notes to me
     └─ ovk (outgoing)  = Blake2b("veil-ovk", viewingKey)  → recover notes I sent (→ disclosure)
masterPublicKey  MPK = Poseidon(spendingPubKey.x, spendingPubKey.y, nk)
```

**Address.** Base address encodes `(MPK, viewingPubKey)`. **Diversified addresses:** a diversifier
`d` (encrypted index) yields an unlinkable address string that still scans under the same `ivk` and
spends under the same key — so an agent hands every payer a fresh address with zero extra key
management. (Diversifier mechanism validated in the Phase 2.0 spike; if it proves costly in-circuit,
MVP falls back to RAILGUN-style single address + per-note `random` for on-chain note unlinkability,
with diversified addresses as a fast-follow.)

**Watch-only:** exporting `ivk` yields a view-only wallet (balances/history, no spend).

**Recovery:** seed → re-derive keys → rescan chain via indexer → rebuild note DB + witnesses.
Nothing else is ever stored server-side.

## 5. Note & commitment
```
note        = { value: u64, asset_id: Field, npk: Field, random: Field }
npk         = Poseidon(MPK, random)                       // per-note owner tag (unlinkable)
commitment  = Poseidon(npk, asset_id, value)              // the Merkle leaf
nullifier   = Poseidon(nullifyingKey, leafIndex)          // revealed on spend; owner-only
```
- `value` range-checked `< 2^64`.
- `asset_id` = an on-chain-registered **index** (u32) for the SPL mint (a `register_asset` ix maps
  index → mint + vault). Keeps the field small and vault lookup O(1); the circuit treats it opaquely.
- `random` blinds the owner and makes notes to the same MPK unlinkable on-chain.

## 6. Transaction model — 2-in / 2-out join-split
One instruction type carries all flows via `publicAmount`:
- `publicAmount > 0` → **shield** (public tokens enter; SPL moves into the vault).
- `publicAmount = 0` → **private transfer** (fully internal; no address on-chain).
- `publicAmount < 0` → **unshield** (SPL leaves to a transparent recipient).

Value invariant (single asset per tx): `Σ in.value + publicAmount = Σ out.value + fee`.
Unused input/output slots are **dummy** notes (`value = 0`, membership check disabled for dummies).
`extDataHash` binds the public leg (recipient address, relayer/fee, asset) into the proof to prevent
front-running/tampering (Phase-1 recipient-binding, generalized).

## 7. Circuits

### 7.1 Transaction circuit (`transaction`, 2-in/2-out)
**Public inputs:** `merkleRoot`, `nullifier[2]`, `outCommitment[2]`, `publicAmount`, `assetId`,
`extDataHash`. (≈ 8 field elements → within Solana tx/CU budget; confirmed against Phase-1 sizing.)
**Private inputs:** per input `i`: `{value, assetId, npk, random, spendingKey, viewingKey, leafIndex,
merklePath, isDummy}`; per output `j`: `{value, assetId, npk, random}`.
**Constraints:**
1. For each real input: `commitment = Poseidon(npk, assetId, value)`; `npk = Poseidon(MPK, random)`
   with `MPK` derived from the spender's keys (proves ownership); Merkle membership of `commitment`
   under `merkleRoot`; `nullifier = Poseidon(nk, leafIndex)`.
2. For each output: `outCommitment = Poseidon(npk_out, assetId, value_out)`; `value_out < 2^64`.
3. All inputs/outputs share `assetId`.
4. `Σ in.value + publicAmount = Σ out.value + fee`.
5. No duplicate input nullifiers; dummy inputs skip membership (their `value = 0`).
6. `extDataHash` bound (squared, as in Phase 1) so it can't be malleated.

### 7.2 Disclosure circuit (`disclosure`)
Proves a single output opens to revealed values, scoped to one verifier + nonce.
**Public inputs:** `commitment` (the on-chain leaf being disclosed), `revealedValue`, `revealedAsset`,
`revealedRecipient` (the recipient MPK), `verifierPk`, `nonce`.
**Private inputs:** `npk`, `random`. (The opening `{npk, random, value, asset, recipient}` is
obtained off-circuit — the sender recovers it via `ovk`, the recipient via `ivk` — so either party
can attest; soundness comes from the opening hashing to the real on-chain commitment, not from who
runs it.)
**Constraints:** `commitment = Poseidon(npk, revealedAsset, revealedValue)`; `npk =
Poseidon(revealedRecipient, random)`; a binding term over `(verifierPk, nonce)` (e.g. squared) so the
proof is non-replayable to another verifier. Off-chain-verifiable (auditor runs the Groth16 verifier);
no on-chain program needed for MVP.

## 8. Note encryption & discovery
Per output note, publish a ciphertext so the recipient can find and open it:
```
eph_sk random (Baby Jubjub); eph_pk = eph_sk · G
shared = ECDH(eph_sk, recipient.viewingPubKey); k = Blake2b(shared)
ct = ChaCha20Poly1305_enc(k, {value, assetId, random, memo?})
```
Also publish an **outgoing** ciphertext keyed from the sender's `ovk`, so the sender can later
recover/disclose the note. Recipients **trial-decrypt** each tx's `ct` with `ivk`; matches are theirs.
Ciphertexts are emitted (event/log or a companion account) — kept out of the 1232-byte proof tx where
size demands it.

## 9. Selective disclosure protocol
1. **Issue:** sender picks an output they sent (recovered via `ovk`), a `verifierPk`, and a fresh
   `nonce`; generates the `disclosure` proof (§7.2) + the revealed tuple.
2. **Deliver:** hand the package to that verifier only.
3. **Verify:** verifier checks the Groth16 proof and that `commitment` is a real on-chain leaf
   (queries the pool/indexer). Success ⟹ "this exact commitment is `value` of `asset` to `recipient`."
4. **Scope:** nothing else is revealed; not replayable to another verifier (nonce+verifier bound);
   "revoked" by not issuing more. Contrast: a viewing key would reveal all payments forever.

## 10. On-chain program & accounts (Anchor)
- **Pool account:** authority, `assetId`→vault map, verifier program id, incremental Merkle tree
  state (`filled_subtrees`, `zeros`, `roots` ring buffer, `next_leaf_index`) — reuses Phase-1 tree.
- **Vault(s):** per-asset PDA holding shielded SPL (ATA owned by a pool PDA).
- **Nullifier PDAs:** one PDA per spent nullifier; `init` = double-spend guard (Phase-1 pattern).
- **Verifier program:** Sunspot Groth16 verifier for the `transaction` circuit; called by CPI.
- **Instructions:**
  - `init_pool`
  - `register_asset(mint)` → assigns a `asset_id` index + creates its vault
  - `transact(proof, public_inputs, extData)` — verifies proof by CPI, checks root known + nullifiers
    unspent, inserts the 2 output commitments into the tree, spends the 2 nullifiers, and moves SPL
    in/out of the vault per `publicAmount` (shield: pull from payer; unshield: pay `extData.recipient`).
  - (ciphertext publication: via event/log or a `publish_notes` companion ix.)

## 11. Off-chain components
- **Indexer:** follows the program, serves commitments + tree state + note ciphertexts (so wallets
  don't scan raw ledger). Untrusted (verifies against on-chain roots).
- **Wallet/SDK (TS):** key derivation, address generation, trial-decryption, note DB + witness
  maintenance, proof generation (nargo + sunspot), tx assembly, disclosure issuance/verification.
- **Prover:** Noir circuits compiled via Sunspot; proofs generated client-side.

## 12. Threat model
**Hidden:** amounts, note owners/recipients (no address on-chain for transfers), the deposit↔spend
link. **Visible (accepted):** that *a* shielded tx occurred, its timing, the public leg of
shield/unshield (a transparent address + amount necessarily appear), the anonymity-set size.
**Mitigations:** front-running via `extDataHash` binding; double-spend via nullifier PDAs; fake-value
roots impossible (root recomputed on-chain, Phase-1 lesson). **Residual/metadata:** timing/graph
analysis, indexer availability, relayer trust for gasless unshield (relayer sees the public leg only).
**Key loss:** losing the seed loses the funds (bearer instrument, by design).

## 13. Solana budgets
- Tx ≤ **1232 bytes**: Groth16 proof (~256 B) + ~8×32 B public inputs + accounts fit; ciphertexts go
  to a companion ix/log. **2-in/2-out is chosen to stay inside this.**
- CU: verify ~200–500K (needs `SetComputeUnitLimit`); insert 2 leaves = 2×depth syscall hashes.
  Validate the combined `transact` CU in Phase 2.2; split into two ixs if over budget.

## 14. Phased roadmap (each phase ends with a runnable, verified artifact)
Each phase gets its own implementation plan (via the writing-plans step) when we reach it — this spec
defines the whole MVP; we plan and build one phase at a time.
- **2.0 — Crypto lib + spike.** Rust/TS lib: Baby Jubjub keys, Poseidon, note/commitment/nullifier,
  KDF, address + diversifier encode, note AEAD. Noir spike validating Baby Jubjub/EdDSA/diversifier
  cost. *Verify:* unit tests + a Noir toy proof using the primitives.
- **2.1 — Transaction circuit.** Noir 2-in/2-out `transaction` circuit + tests; Sunspot verifier
  built; local prove/verify for shield, transfer, unshield witnesses. *Verify:* off-chain verify green.
- **2.2 — On-chain program.** Anchor pool + tree + nullifier PDAs + vault + `transact` CPI-verify +
  SPL moves. *Verify:* local validator e2e — shield → private transfer → unshield with real proofs;
  double-spend + front-run rejected.
- **2.3 — Notes & discovery.** Note encryption, indexer, wallet trial-decrypt + note DB + witnesses.
  *Verify:* recipient discovers a transfer sent to them and can spend it.
- **2.4 — Selective disclosure.** `disclosure` circuit + issue/verify flow (per-verifier, nonce-bound).
  *Verify:* disclose one payment to a verifier; verify; confirm no other payment is learnable.
- **2.5 — SDK + agent demo.** TS SDK + an agent-payment demo (fresh diversified address per payer;
  private pay; on-demand disclosure). Optional: relayer/paymaster for gasless unshield.

## 15. Open items to resolve during 2.0 (not blocking the spec)
- Exact diversifier construction + its in-circuit cost (else single-address fallback).
- Fee model (protocol fee? relayer fee only?) — default MVP: no protocol fee, relayer fee via extData.
- Whether `transact` fits one tx/ix or must split verify vs. state-update.
